# Project rules

- **The site is English-only.** Everything under `site/` — page text, UI strings, notices and error messages, `title`/`aria-label` attributes, code and CSS comments — must be in English. Do not add strings in other languages.
- **No mobile version, by decision (2026-10-27).** The site is for windows of at least 800 × 640 px (computers, tablets held sideways). Do not add phone or small-screen layouts, scrolling fallbacks or media queries for them. Below that size `fullscreen.js` shows a notice (`.fs-small`, `fullscreen.css`) instead of the page: it says the window is too small and how big it is, suggests a bigger screen or the browser's full-screen mode, and says what the site does; keep that description true when pages or features change. The limit is one number in three places (the media query in `fullscreen.css`, the text in `fullscreen.js`, `tools/fullscreen-test.mjs`): change them together, and only after checking that every page fits at the new size. `site/landing/` is a presentation page that scrolls and is not part of this layout.
- **Effects List text is verbatim.** Effect and parameter descriptions in `site/effects-data.js` are copied exactly from the official ZOOM MS-60B+ Effects List; never translate or paraphrase them.
- Link the English ZOOM manual: `https://zoomcorp.com/manuals/ms-60bplus-en/#unique_41`. The Resources page, linked from the Guide (`site/resources.html`, `site/ms-50g/resources.html`) lists the manuals in English and Italian and the Effects List PDF; it also links the Italian one (`https://zoomcorp.com/manuals/ms-60bplus-it/`); every other link points to the English manual. Use `.` as the decimal separator and `en-GB` date formatting.
- The `.zptc` codec lives in `site/zptc.js` and is shared with `tools/zptc.mjs`. After changing it, run `node tools/zptc.mjs roundtrip patches/0* "patches/07Big Black .zptc"`: every file must round-trip byte for byte. Format notes: `docs/zptc-reverse-engineering.md`.
- Advice engine: `site/advice-engine.js` runs the rules; rules, placement tips and style profiles live in `site/advice-rules.js`. Every rule must cite at least one source (`ADVICE.addSources`) unless it is an objective fact about the pedal. Effect order is convention: order rules are `warning` or `tip`, never `error`. Check the source links now and then with `node tools/check-sources.mjs` (TalkBass blocks scripts and shows as "blocked"; open it in a browser). Rule packs (`site/rule-packs.js`) let users import their own rules as `.json`: keep them data-only and source-required. After changing rules, rule packs or starter chains run `node tools/advice-test.mjs` (starter chains must encode, stay under 100% DSP and raise no errors or warnings).
- Accounts (phase 1 of `docs/piano-login.md`): `deploy/accounts.mjs` (routes `/login`, `/register`, `/forgot`, `/reset`, `/verify`, `/logout`, `/api/me`), `auth.mjs` (PBKDF2, signed cookie `zms_session`, tokens, rate limits, CSRF), `db.mjs` (SQLite via `node:sqlite`, `DATA_DIR/studio.db`), `mail.mjs` (Gmail SMTP and Telegram like PatternMachine), `pages.mjs`. After changing any of them run `node tools/auth-test.mjs`. Account sync: `deploy/account-sync.mjs` (`POST /api/account/sync/<pedal>`, tables `patches` and `docs`) with the browser side `site/account.js` (syncs both pedals: `-library`, `-deleted` and the docs `-advice`, `-view`, `-builder`, `-rulepacks`, `-usb-backups`; merge rules `LIBMERGE.mergeDocs`); after changing them run `node tools/sync-test.mjs`. Secrets stay on the server, never in git: `mail.json` (`node set-mail.mjs`), `telegram.json` (`node set-telegram.mjs`), `.env` (`SITE_URL`, `SESSION_SECRET`, `MAIL_FILE`, `TELEGRAM_FILE`) in `/srv/apps/zoom-ms60b-app/`. Admins are created on the server with `node add-user.mjs --email … --admin`; they get the user console `/admin` (`deploy/admin-pages.mjs`, routes in `accounts.mjs`: search and sort accounts, reset link, sign out everywhere, make/remove admin, download data, delete with confirmation, read-only patch list, service state; every action goes to `admin_log`; an admin never acts on their own account).
- Sync: `site/library-merge.js` (merge rules) is shared with `deploy/server.mjs`, which serves the site and the account sync API (the anonymous `/api/sync/<code>` was removed in 2026-10 and answers 410). After changing either, run `node tools/sync-test.mjs`. Account interface in `site/account.js` (loaded by every pedal page with `library-merge.js`): "Sign in" or the account menu in `.gh-header`, the signed-out notice on pages with `<body data-account-notice>`, `.account-local` labels shown only when signed out, the first-sign-in choice and sign-out (default: remove the data from this browser). After UI changes in the builder run `PW_CHANNEL=chrome node tools/e2e-test.mjs` (Playwright; `npm install` first). The accounts database is backed up daily by `deploy/backup-data.sh` (`db-backup.mjs`, `VACUUM INTO`; user crontab on the server, archives in `/srv/apps/zoom-ms60b-backups`, 30 days). `site/privacy.html` describes what is stored: update it when the stored data, the emails or the backups change. Server files go to `/srv/apps/zoom-ms60b-app/` on the server (`rsync -a deploy/*.mjs deploy/backup-data.sh giovanni@100.81.62.48:/srv/apps/zoom-ms60b-app/`, then `ssh -t giovanni@100.81.62.48 'sudo systemctl restart zoom-ms60b.service'`, which needs the user's password), the database `studio.db` lives in `/srv/apps/zoom-ms60b-data` (outside the web root, never deploy over it).
- Pedal manager over USB (`site/pedal-manager.html`, experimental: lists the pedal memories next to My patches, reads, and writes with backup): `site/pedal-midi.js` speaks the SysEx protocol of zoom-zt2 (MIT, undocumented by ZOOM). After changing it run `node tools/midi-test.mjs` (simulated pedal in `tools/fake-pedal.mjs`). Never add a write command without a backup of the target memory and a read-back check.
- Interface (Panels layout, both pedals): every page is laid out so the page never scrolls and long lists scroll inside their pane (`site/fullscreen.css`, `site/fullscreen.js`: pedal menu, contents list of the documents, small-screen notice). Pages: `index.html` (Effects), `builder.html`, `tones.html`, `pedal-manager.html`, `resources.html`, `technical-notes.html`, `privacy.html` (its text is in the page), `guide.html`, and the same for the MS-50G+ in `site/ms-50g/` (`index`, `builder`, `resources`, `guide`; no Pedal manager or Tone ideas, a "Not tested" bar under the header). Page text of the two pedals mirrors each other: carry text changes over by hand. `guide.html` is the how-to (the Guide button is top right, before the account menu): keep it true to what the pages do; the how-to for loading a patch on the pedal lives only there, and the Resources page is linked from it, not from the status bar. The Effects detail is a pane next to the list (`app.js`: no previous/next buttons, "Add to patch" under the description). Advice has no on/off switch. The Patch builder has three columns: the chain, the patch with Advice under it, and My patches at the right. The status bar has the tongatron.org button (B3 of tongatron.org/pulsanti) all the way to the left, then Source on GitHub and Privacy, and the update time at the right; the ZOOM data note (© 2024 ZOOM CORPORATION, manufacturer names) is in the "Data and credits" section of each Guide, not in the bar. In the pedal menu the MS-60B+ has the green tag "Tested on firmware 1.20" (change it when the tested firmware changes) and the MS-50G+ "Not tested". `site/_fullscreen/` only holds redirects from the old test addresses. After layout changes run `PW_CHANNEL=chrome node tools/fullscreen-test.mjs` (both pedals, all pages and sizes). Plan and to-dos: `docs/piano-fullscreen.md`.
- Tone ideas (`site/tones.html`, `site/tones.js`, data in `site/tone-ideas.js`): every bassist fact cites a source key from `advice-rules.js`; styles come from the advice styles with a starter. Share links (builder and Tone ideas) use `site/patch-link.js`.
- Deploy: run `node tools/stamp-update.mjs` first ("Last update" under the GitHub link in every footer), commit, then `rsync -a --exclude '.DS_Store' site/ giovanni@100.81.62.48:/srv/apps/zoom-ms60b/` (served at https://zoom.tongatron.org). Deploy over Tailscale: `100.81.62.48` is the node `hp-ubuntu`; the `hp-ubuntu` SSH alias points to `giovanni-pc-ubuntu.local`, which only works on the home LAN (from Claude Code the SSH connection needs the sandbox off). Bump the `?v=` query strings in the HTML when CSS/JS change; if a deploy is interrupted, bump them again before redeploying, because Cloudflare may have cached the old file under the new URL.
- Second pedal: **Zoom MS-50G+ (guitar), "not tested"** in `site/ms-50g/` (own `pedal.js`, `effects-data.js`, `firmware-data.js`, `advice-rules.js`, effect images; shared scripts and CSS from `site/`). `site/pedal.js` holds the MS-60B+ settings; shared scripts read `PEDAL` for URLs and the storage/sync prefix. MS-50G+ data comes from `python3 tools/extract-effects-list.py documentazione/ms-50gplus/E_MS-50Gplus_EffectsList.pdf` (verbatim, checked word for word against the PDF) and zoom-zt2 `ms-50gp/effects_sort.txt`; the 24 ★ Handy Guitar Lab add-ons have no firmware entry (`null`) and stay out of the builder. Its advice is objective checks only: add guitar rules with guitar sources, never reuse the bass ones. Page text in `site/ms-50g/*.html` mirrors the MS-60B+ pages: carry layout changes over by hand.
